# FitBuddy 需求设计（V1）

> 状态：待确认 · 最后更新 2026-07-27

## 1. 一句话定义

一个发到朋友群里就能用的网页，让 3–8 个朋友互相看见彼此的减肥运动打卡，谁偷懒一眼可见。

## 2. 问题本质

先想清楚为什么需要它，再决定做什么功能。

减肥失败的原因几乎从不是"不知道该做什么"，而是**没人看着**。市面上的健身 App 把重心放在数据记录（卡路里、组数、动作库），这解决的是"专业度"问题，而不是"坚持"问题。

所以本项目的第一性设计结论：

| 真正起作用的机制 | 本项目怎么落地 |
|---|---|
| **可见性** —— 我不打卡，朋友立刻知道 | 打卡墙：本周 7 天 × 全员，空格就是耻辱柱 |
| **连续性损失厌恶** —— 已连续 12 天，不想断 | streak 连续天数 + 断卡红色标记 |
| **同侪对比** —— 别人做到了，我做不到很难看 | 减重百分比排行（不比绝对体重） |
| **代价** —— 断卡要付出东西 | V1 只做「欠账记账」，不做支付（见 §7） |

**反向结论：以下功能不做**，因为它们不解决坚持问题，只增加摩擦——动作库、卡路里计算、饮食记录、健身计划生成、社交动态流。

## 3. 用户与场景

- 用户：Bindy + 3~7 个朋友，彼此认识、互相信任，都用手机。
- 典型场景：晚上跑完步，掏出手机，点开群里的链接，**两秒内完成打卡**，顺便看一眼谁今天还空着，去群里艾特他。

关键约束：**手机优先**。桌面端只需不难看，不需要优化。

## 4. 核心设计决策

### 4.1 不做注册登录

只有几个熟人，账号体系是纯负担。方案：

1. 建组时生成一个邀请链接 `/g/{6位小组码}`。
2. 朋友第一次打开 → 选「我是谁」（列表里点自己）或「我是新人」输入昵称 → 身份存 localStorage。
3. 之后打开链接直接就是自己的视图。

代价：同组的人理论上能冒充别人打卡。熟人小组里这不是问题，而且互相监督的场景下**没人有动机替别人打卡**。用信任换掉整个账号系统，值得。

### 4.2 体重默认不公开绝对值

体重基数不同，绝对数字既不公平也让人抗拒参与。默认只对外显示**减重百分比**（相对各自起始体重），绝对体重仅自己可见。设置里可以主动选择公开。

这一条在数据库层生效，不只是界面上不显示：排行榜读的是 `member_progress` 视图，未公开体重的成员，视图直接返回 `null`，别人的公斤数不会进到前端。

### 4.3 打卡就是一次点击

主按钮「今天动了 ✓」点完立即完成，其余全是可选的：运动类型、时长、一句话、体重。**不填任何东西也算有效打卡**——摩擦每增加一点，坚持率就掉一截。

### 4.4 补卡受限

只能补**昨天**，且带「补」标记，**滚动 7 天内最多 1 次**。完全禁止补卡太严苛（真有忘记的时候），无限补卡则打卡墙失去意义。

额度按滚动 7 天算而不是按日历周算：否则周一补周日的卡会记在「上一周」的额度里，等于每周能白补两次。

补卡入口放在打卡按钮下方，不只藏在打卡墙的格子里 —— 周一时昨天（周日）属于上一周，格子根本不在画面上。

## 5. 功能清单

### V1（第一版，必须做）

| # | 功能 | 说明 |
|---|---|---|
| F1 | 建组 / 加入组 | 建组填：组名、打卡目标（每周几天）、单次最低时长；生成邀请链接 |
| F2 | 身份识别 | 选自己是谁，localStorage 记住 |
| F3 | 一键打卡 | 主按钮完成当日打卡，可选填运动类型 / 时长 / 一句话 |
| F4 | 打卡墙 | 本周 7 列 × 全员行的网格，✓ / 空 / 补，一眼看完；最后再加一列「上周达标天数」，否则周一整面墙是空的，等于没有信息 |
| F5 | 连续天数 | 每人当前 streak + 历史最高 streak |
| F6 | 本周达标状态 | 对照小组目标（如每周 5 天），显示「3/5，还差 2 天」 |
| F7 | 体重记录 | 自己录入体重，看自己的曲线；对外只出百分比 |
| F8 | 减重排行 | 按减重百分比排序 |
| F9 | 个人页 | 某人的打卡历史 + 曲线，点头像进入 |

### V2（确认 V1 好用之后再做）

- 欠账记账：断卡自动记「欠 X 元 / 欠一顿饭」，只记账不收钱
- 提醒推送：晚上 21:00 未打卡的人收到提醒（浏览器通知，或推到飞书 / 微信群机器人）
- 打卡照片
- 互相评论 / 戳一下
- 每周日自动生成周报卡片，可直接截图发群

### 明确不做

动作库、卡路里、饮食记录、AI 训练计划、陌生人社交、积分商城。

## 6. 界面结构

移动端三个页面，底部无导航栏（三页之间靠内容跳转，减少 chrome）：

```
首页 /g/{code}
├─ 顶部：本周目标进度「还差 2 天 · 本周还剩 4 天」+ 3/5
├─ 主按钮：今天动了 ✓        ← 打过卡则变为「今天已打卡 · 连续 12 天」
├─ 补卡入口（仅在昨天空着且额度还有时出现）
├─ 打卡墙                    ← 核心区域，本周 7 天 × 全员 + 上周成绩
│    一 二 三 四 五 六 日 上周
│  我 ✓ ✓ · ✓ ✓ 补 —   4
│  A  ✓ ✓ ✓ ✓ ✓ ✓ —   7
│  B  ✓ · · · ✓ · —   2   ← 空格多、上周数字红的人自然显眼
└─ 减重排行（前三 + 我的位置）

个人页 /g/{code}/m/{id}
├─ streak、本月打卡天数、减重百分比
├─ 体重曲线（自己看得到数字，别人看不到）
└─ 打卡历史列表

设置 /g/{code}/me
└─ 昵称、起始体重、目标体重、是否公开体重
```

视觉原则：打卡墙必须**不滚动就能看完全组**（8 人 × 7 天在手机上放得下），这是整个产品的信息核心。

## 7. 惩罚机制（需 Bindy 决策）

这是最能提升坚持率的机制，但涉及钱，所以拆开：

- **方案 A（推荐，V2 做）**：只记账。断卡 → 自动记「欠账」，界面显示「B 累计欠 3 顿饭」，线下结算。零支付风险，社交压力照样成立。
- **方案 B**：接入真实支付 / 押金池。需要收款主体、退款规则、纠纷处理，V1 不碰。
- **方案 C**：不做惩罚，只靠可见性。

**已决策：V1 按方案 C 交付（不做惩罚，只靠可见性）**，数据结构预留欠账字段，V2 再上方案 A。

## 8. 技术方案

**已决策：Supabase + Vercel。**

| 层 | 选择 | 理由 |
|---|---|---|
| 前端 | Vite + React + TypeScript + Tailwind | 手机端布局快，组件化，后续加功能不会烂 |
| 数据 | Supabase（Postgres + JS SDK） | 互相监督必须共享数据，纯前端 localStorage 做不到；Supabase 免费额度足够几个人用，不用自己写后端 |
| 部署 | Vercel 或 Cloudflare Pages | 推一次得到一个可分享链接 |
| 图表 | 轻量 SVG 自绘或 Recharts | 只有一条体重折线，不值得引重库 |

需要 Bindy 注册两个免费账号（Supabase、Vercel），配置步骤见 [README](../README.md)。Supabase 只使用 anon key，配合 RLS 策略限制为「凭小组码读写本组数据」：前端每个请求带 `x-group-code` 请求头，数据库只放行请求头里那个码对应的小组，所以拿到 anon key 也无法遍历别人的小组。

**没配 Supabase 时会进入演示模式**：数据只存本机 localStorage，并自动放三位示例成员，方便先看界面。演示模式下朋友之间不共享数据，界面顶部有明确提示。

## 9. 数据模型

```
groups
  id            uuid pk
  code          text unique     -- 6 位邀请码
  name          text
  target_days   int             -- 每周目标打卡天数，默认 5
  min_minutes   int             -- 单次最低分钟数，默认 30，0 表示不限
  created_at    timestamptz

members
  id            uuid pk
  group_id      uuid fk
  name          text
  emoji         text            -- 代替头像上传
  start_weight  numeric null    -- kg
  target_weight numeric null
  show_weight   bool default false
  created_at    timestamptz

checkins
  id            uuid pk
  member_id     uuid fk
  date          date            -- (member_id, date) unique
  exercise      text null       -- 跑步 / 力量 / 骑行 / 游泳 / 其他
  minutes       int null
  note          text null
  is_makeup     bool default false
  created_at    timestamptz

weights
  id            uuid pk
  member_id     uuid fk
  date          date            -- (member_id, date) unique
  kg            numeric
```

streak、达标进度、减重百分比全部由 checkins / weights 实时算出，不落库，避免状态不一致。

## 10. 验收标准

V1 做完时，下面每条都成立：

1. 把链接发进群，朋友点开 → 30 秒内完成首次打卡，不需要任何口头说明。
2. 打卡从点开链接到完成 ≤ 2 次点击。
3. 首页不滚动就能看出全组本周谁在偷懒。
4. 换手机 / 清缓存后重新选身份，历史数据仍在。
5. 手机竖屏无横向滚动、无文字截断。
6. 没人问「这个按钮是干什么的」。
